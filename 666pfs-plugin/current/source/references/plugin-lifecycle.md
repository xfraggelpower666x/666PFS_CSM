Read current/PLUGIN_CURRENT.json, continuity/PLUGIN_REHYDRATION.md, continuity/PLUGIN_LIFECIRCLE.md, continuity/PLUGIN_BACKUP_STATE.md, governance/MANAGED_PLUGIN_BACKUP_ROUND_GOVERNANCE.md, governance/UPDATE_INGEST_AND_PLUGIN_EVOLUTION_STANDARD.md and recovery/RESTORE_CONTRACT.md from verified current PFS HEAD. Those current contracts override this reference. Keep exact plugin ID and existing audience/permissions. Plugin Builder is the executable surface; repo source is PFS-owned source/parity/recovery authority; backup child only tracks recovery and never owns live authority.

Every PFS UPDATE must first inspect direct user instructions plus relevant inbound recommendations, handoffs and proposals. Classify each as VERIFIZIERT, ABGELEITET, VORGESCHLAGEN, OFFEN or BLOCKIERT. After PFS compatibility audit, implement verified durable PFS-relevant deltas in the same native update when safe and authorized. Foreign proposal presence never creates foreign authority.

Every PFS UPDATE must also inventory all PFS-managed plugin backups and compare live version, release ID, runtime fingerprint, repository parity, binary parity where applicable, and development impact. If a managed plugin evolved, it becomes a backup-round candidate. Complete PFS-owned plugin evolution before any external backup request.

Before any foreign/private backup-round request, freeze one stable managed-plugin set. Inform LYVRA and CLIC once per stable set, request each system's own native backup authorization, and explicitly tell LYVRA that the coordinated round is intended for private-repository plugin-backup integration. LYVRA live repository remains approval authority; the LYVRA private repository remains backup storage only. A fingerprint or release change breaks the stable set and requires a new candidate round.

Every PFS UPDATE must classify plugin impact: NO_PLUGIN_CHANGE_REQUIRED, PLUGIN_UPDATE_REQUIRED, PLUGIN_UPDATE_BLOCKED, PLUGIN_READBACK_PENDING or PLUGIN_PARITY_REPAIR_REQUIRED. Check rehydration, daemon, LifeCircle, CSM, child lifecycle, Scope Map, handoff, backup, triggers, authority, dashboard, continuity and managed-plugin backup-round governance. Do not bump versions without semantic impact. Relevant verified PFS evolution requires governed plugin evolution and backup, subject to actual tooling and permissions.

Before plugin evolution verify PFS HEAD, locks, allowlist, current plugin release and pre-change recovery. Preserve immutable snapshots. Prepare repo source and release snapshot, update existing plugin with expected_release_id, read live release back, compare file lists and actual text/binary bytes, capture real SHA-256/size/entry list, write backup, directly read it back, compare hash, record receipt, update backup child and continuity, freeze, then publish the PFS pointer last. No mutation afterwards in the same update. If interrupted preserve return anchor and exact pending phase. Never label archive availability as verified backup.

PFS may authorize its own plugin backup; foreign system approval is not needed for its own plugin. Foreign backup legs still require their own native authorization. PFS coordinates the round but never self-approves LYVRA or CLIC.

Backup child must be bound only through current PFS child identity governance. Never guess a current child ID or reuse a foreign plugin child. If unresolved, record OPEN instead of inventing a binding. Backup child source bindings must include plugin/release/version, immutable snapshot, fingerprint, text and binary parity, archive SHA-256/size/path/receipt, readback and restore status.
